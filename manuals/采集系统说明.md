# 采集系统说明（学院资讯 / 竞赛信息）

> 面向「AI 芯动力」官网维护者。本文回答三件事：**它怎么工作**、**怎么加一个源**、**坏了怎么修**。
> 代码：`scripts/collect.py`（纯 Python 标准库，无第三方依赖）　配置：`sources/sources.json`

---

## 1. 一句话概括

每天跑一次 `python3 scripts/collect.py`，把 5 个学校/竞赛官网的**公开列表页**抓下来，
用正则抽出「标题 + 原文链接 + 日期」，去重、过异常拦截、写入 `content/collected/<源 id>.json`。
**只存结构化字段和原文链接，绝不转载全文**；抓到的每一条都在页面上标注「信息来源：XX 官网 ↗」。

设计参考 pyzw618/UESTC-Teamup 的 `docs/MODULE_CRAWLER.md`（那个模块后来被删了，文档保留作设计参考）。

## 2. 流水线：为什么是这个顺序

```
读 sources.json
      │
① robots.txt 检查 ── Disallow → 直接放弃这个源（合规红线，不商量）
      │
② Fetcher ── urllib，超时 20s、重试 2 次（只重试 429/5xx）、串行、源间隔 ≥3s
      │        ⚠ UA 里带中文会让【所有】请求同时挂掉，见 §5.1
      ▼
③ 编码解码 ── HTTP header charset > <meta charset>(前 2KB) > utf-8
      │        ⚠ GBK 站点是"静默失效"头号原因，见 §5.2
      ▼
④ 容器预检 ── list_selector 还在不在（页面改版探针）
      ▼
⑤ Parser ── item_pattern 正则 → {title, url, date_text}
      ▼
⑥ 日期抽取 ── 五种格式 + 缺年补全，抽不出来就留空，见 §5.3
      ▼
⑦ 去重 ── SHA256(title|url)[:16] 作为 id，对着「见过全集」比对，见 §5.4
      ▼
⑧ Guard 异常拦截 ── 六条规则，命中就不发布（写盘之前！）
      ▼
⑨ Publisher ── 写 content/collected/<源 id>.json（locked:true 的条目永不覆盖）
      ▼
⑩ 健康度 + 状态 ── content/collected/_state.json
```

**关键纪律：先有刹车，再踩油门。** Guard（第 ⑧ 步）必须在任何写盘之前完成。
这也是为什么 `--dry-run` 会跑完 ①~⑧ 全流程但什么都不写。

## 4. 怎么用

```bash
cd /mnt/c/Users/swat/Desktop/uestc-aic-website

# 只抓不写，看条数（改完选择器后必跑）
python3 scripts/collect.py --dry-run --verbose

# 跑全部启用源并写盘
python3 scripts/collect.py

# 只跑某个源（排查单源问题）
python3 scripts/collect.py --source mcm-notice --verbose
```

| 参数 | 作用 |
|---|---|
| `--dry-run` | 抓取 + 解析 + 去重 + Guard 全跑，**不写任何文件**（连 `_state.json` 都不动） |
| `--source <id>` | 只跑指定源（可重复；默认跑全部 `enabled: true` 的源） |
| `--verbose` / `-v` | 打印每一步细节：robots 结果、编码、命中数、Guard 命中、样例条目 |
| `--interval <秒>` | 覆盖源之间的间隔（默认 3s，且不小于 robots 的 Crawl-delay） |

### 产出文件

```
content/collected/
├── <源 id>.json        每个源一个文件，只留最近 30 条（max_items_per_source）
├── _state.json         健康度 / 连续 0 条天数 / 见过的 id 全集
└── _anomalies.json     Guard 拦截记录（最多留 500 条）
```

单条记录长这样（**只存结构化字段 + 原文链接**）：

```json

```

## 5. 四个最容易翻车的地方（都是实测踩出来的）

### 5.1 UA 里不能有中文 ⚠️

第一次跑，**5 个源全军覆没有**，报错都是同一句：

```
'latin-1' codec can't encode characters in position 57-65: ordinal not in range(256)
```

原因：HTTP 头按 latin-1 编码，形如 `AIC-UESTC-Crawler/1.0 (… AI 芯动力社区资讯采集)` 的 UA 里
只要有一个中文字符，**每一个请求**都会在发出去之前就抛异常。而且它不像"某个源坏了"，
是"所有源同时挂了"——很容易误判成网络问题。

修法：UA 用 ASCII（现在写的是 `AIC-UESTC-Crawler/1.0 (+https://github.com/uestc-aic; AI-for-IC community news collector) …`），
并且 `fetch()` 里加了一道 `re.sub(r"[^\x20-\x7e]", "", ua)` 兜底，配置再被写脏也不会整轮采集报废。

**同时**：UA 必须明确标识自己是谁（`AIC-UESTC-Crawler/1.0 (+仓库地址)`），这是合规要求，
不要伪装成纯浏览器 UA。

### 5.2 编码：国内高校站的 GBK 陷阱（静默失效头号原因）

优先级 **HTTP header charset > `<meta charset>`（只看前 2KB）> 默认 utf-8**，
解码一律 `buf.decode(charset, errors="replace")`。

两个坑：

1. **`gb2312` 要当成 `gbk` 解。** 声明 `charset=gb2312` 的站点，正文里几乎必然有 GBK 超集字符。
   用 `gb2312` 严格解码会失败，退化成 `errors="replace"` 就得到一片 `�` ——
   然后日期正则全部匹配不到，**而且不报错**，只是悄悄抓不到东西。代码里做了别名映射。
2. **`<meta charset>` 要用 bytes 正则找**，不能先 decode 再找 —— 那正是要解决的问题。

实测这条逻辑不是摆设：`news.uestc.edu.cn` 的响应头是 `Content-Type: text/html`，**根本没有 charset**，
只有正文 `<meta charset="UTF-8">` 兜底，全靠第 2 级判断。

### 5.3 中文日期抽取：抽不出来是最常见且正常的结果

覆盖的格式（按优先级，见 `_DATE_RES`）：

| 原文 | 规则 | 结果 |
|---|---|---|
| `2026年10月15日` / `2026-10-15` / `2026/10/15` / `2026.10.15` | ① 带 4 位年 | 2026-10-15 |
| `即日起至10月15日` / `报名截止：10月15日` | ② 月日（缺年） | 2026-10-15 |
| `26-09-15`（数模网专用） | ③ 两位年 | 2026-09-15 |
| `10.15` | ④ 点分无年 | 2026-10-15 |
| `09-29`（教务处首页） | ⑤ 纯 MM-DD，**必须整串匹配** | 2026-09-29 |
| `10月下旬` / `详见附件` | **不猜** | 空（不写、不报错） |

**缺年份时怎么补年** —— 这里必须区分两种语义，是 TeamUp 文档没写透、搞错就会整年搞错的地方：

- **`published`（列表页的发布日期）**：年份 = 今年；补出来若是**未来**，说明是去年的。
  （今天 10-15 看到一个 `12-31`，必然是去年 12-31。实测教务处 `12-31` → 2025-12-31。）
- **`deadline`（通知里的"即日起至10月15日"这类截止）**：年份 = 今年；补出来比今天早**超过 90 天**
  （`GRACE_DAYS`），说明是明年的。（10 月看到的 `1月3日` 截止 → 2027-01-03。）

策略由源的 `date_year_policy` 决定（默认 `published`），且日期文本里出现「至/截止/报名/到」等词时
**自动按 deadline 处理**。**注意 `-` 不能算 deadline 关键词** —— 否则 `03-11` 这种发布日期会因为
"比今天早 218 天"被推到明年（这个 bug 真的出现过，教务处 `教授开放日安排表(2026春季)` 被算成 2027-03-11）。

**抽不出来是正常结果。** 程序必须优雅处理：不写入、不报错、不崩溃。本仓现在 5 个源的日期抽取率都是 100%，
但别把这个当默认预期 —— 通知正文里的模糊时间（"10月下旬"、"详见附件"）本来就没法可靠解析，
那些留给人工。

### 5.4 去重：必须对着「见过的全集」，不能只看发布文件

- id = `SHA256(title + "|" + url)` 的前 16 位。标题或链接任一变化就是新条目。
- **`max_items_per_source`（默认 30）会把老条目从发布文件里裁掉。**
  如果去重只跟发布文件比对，被裁掉的旧条目下一轮会被判成"新条目"重新写回来 ——
  列表在 30 条和 49 条之间反复横跳，而且**永远满足不了"第二次新增为 0"**。
  实测过：不修的话第二次运行 `mcm +7`、`uestc-news +19`。
- 修法：`_state.json` 里为每个源存一份 `seen_ids`（见过的 id 全集，最多留 2000 个），
  去重同时比对「发布文件」+「seen_ids」。修完后第二次、第三次运行都是 **新增 0 / 跳过 185**。

> **被 Guard 拦截的条目也记进 seen_ids**，否则每一轮都会为同一条 2010 年的老公告重复报警，
> 把 `_anomalies.json` 淹掉。要重新评估它们：删掉 `_state.json` 里该源的 `seen_ids`（或整个文件）再跑。

## 6. 人工锁定：没有它，人工修正形同虚设

**问题**：管理员手工修正了一个被解析错的日期，下一次采集会把它**改回去** ——
看起来像"数据自己变回去了"这种灵异现象。

**方案**：任何 `locked: true` 的记录，采集**永不覆盖**（连字段都不碰，连标题都不改）。
锁定标记来自两个地方，都会读：

- `content/collected/<源 id>.json` 里任意条目的 `"locked": true`
- `content/events.json` 里任意条目的 `"locked": true`（网站主体内容，人工维护）

命中就计入汇总表的**「锁定」列**（不是"跳过"），一眼能看出这条源有几条是人工在管。

实测验证（2026-10-15）：把 `uestc-gr-competition.json` 第一条改成 `locked: true` 并把标题篡改成
「【人工修正】测试标题-绝不该被采集覆盖」，单独跑该源 → 汇总表 `锁定 = 1`，跑完后文件里
`locked` 仍是 `true`、标题**仍是篡改后的值**。机制有效。

## 7. 异常拦截器（Guard）：六条规则

**这是投入产出比最高的一段代码**，用几条规则挡住最丢人的事故。

| 规则 | 触发条件 | 动作 |
|---|---|---|
| `date-out-of-range` | 年份 < 2020 或 > 2035 | 不发布，记 anomaly |
| `epoch-date` | 抽到 1970 年（解析失败的经典症状） | 同上 |
| `end-before-start` | 日期区间结束早于开始 | 同上 |
| `jump-too-large` | 同一 id 的日期跳变 > 180 天 | 保留旧值，记 anomaly |
| `null-overwrite` | 旧值非空而新值为空 | **保留旧值**，记 anomaly |
| （新条目命中任一规则） | — | **干脆不写进去**（逐源计入"拦截"列） |

**注意它是最后一道防线，不是第一道。** 它拦不住"格式对了但抽错字段"这类错误 ——
那只能靠 §5.3 的日期测试和 §6 的人工锁定 + 事后纠错。

实测：`mcm-notice` 的通知列表里含 2010–2019 年的历史公告，**每轮稳定拦截 60 条**（`date-out-of-range`），
只发布 2020 年以后的。这是**预期行为**，不是 bug。如果确实要展示历史条目，把 `collect.py` 里的
`YEAR_MIN` 调小即可。

## 8. 合规边界（改了要负责任）

- **robots.txt 先查再抓**，`Disallow` 命中就放弃该源（不是"记个警告继续抓"）。
  解析并尊重 `Crawl-delay`，实际间隔取 `max(3s, Crawl-delay)`。
  实测 5 个源的情况：4 个返回 **404**（无 robots.txt = 无限制），`mcm.edu.cn` 返回 **200 + 0 字节**（空文件）。
- **串行抓取，不并发。** 源之间至少隔 3 秒。2C2G 机器上并发只会让内存尖峰叠加，
  而采集根本不需要快 —— 每天跑一次，跑 20 分钟和跑 2 分钟没有区别。
- **只存结构化字段 + 原文链接，不转载全文。** 标题是必要的最小信息量；
  正文只在内存里用于解析，不落盘、不上页面。
- **只抓公开页面**，不绕过登录、不绕验证码。遇到 WAF/412 就登记为停用源（`uestc-icse-portal` 就是这么处理的）。
- **User-Agent 明确标识**。
- 用户可见处标注「信息来源：XX 官网 ↗」，链接指回原文。

## 9. 坏了怎么修

### 9.1 先看健康状态

每次运行结束会打印汇总表：

```
源 ID                         抓取     新增     跳过     更新     拦截     锁定     异常  健康        备注
----------------------------------------------------------------------------------------------------------------
mcm-notice                   97      0     97      0      0      0      0  ok
uestc-news                   49      0     49      0      0      0      0  ok
```

| 健康值 | 含义 | 该怎么办 |
|---|---|---|
| `ok` | 抓到了、解析出了条目 | 什么都不用做 |
| `degraded` | **抓到 0 条** —— 选择器很可能已失效 | 立刻修，见 §9.2 |
| `failing` | 抓取失败（HTTP 4xx/5xx/超时/DNS） | 先 `curl` 手测 URL 是否还活着 |
| `blocked` | robots.txt 不允许 | 不要绕过；换源或找人协调 |
| `disabled` | 配置里 `enabled: false` | 看 `notes` 里的停用原因 |

第 ⑦ 列「拦截」是 Guard 挡下的条数，第 ⑥ 列「锁定」是人工接管的条数。

### 9.2 ⚠️ 最重要的一条告警：连续 N 天抓到 0 条

**网站改版后，爬虫不报错、只是再也抓不到东西，数据会悄悄烂掉。**
全自动发布模式下没人看队列，只能靠这条告警发现。

`_state.json` 里每个源都有 `zero_streak_days`：健康 `ok` 时清零，
`degraded`/`blocked` 时 +1。**连续 ≥3 天就该动手了**：

```bash
# 看当前连续 0 条天数
python3 -c "import json;d=json.load(open('content/collected/_state.json',encoding='utf-8'));print({k:(v['last_health'],v['zero_streak_days']) for k,v in d['sources'].items()})"
```

### 9.3 判断"是不是选择器失效"的标准动作

1. **先确认网页本身还有内容**：浏览器打开目标页，**右键"查看网页源代码"**（不是"检查"）。
   - 源代码里能看到标题 → 服务端渲染，好抓，是我们的正则过时了 → 进第 2 步。
   - 源代码里只有一堆 `<script>`、正文是空的 → 变成 JS 渲染了，正则救不回来 →
     要么找它背后的 JSON API，要么登记 `enabled: false` 并改人工录入（`content/inbox/`）。
2. **`curl` 手测，看命中数**：

```bash
curl -s -A "AIC-UESTC-Crawler/1.0 (+https://github.com/uestc-aic) Mozilla/5.0 ..." \
  "https://目标页" | python3 -c "
import sys,re
h=sys.stdin.read()
print('字节数', len(h))
print('候选条目', len(re.findall(r'<你的item正则>', h)))"
```

3. **对比命中数。** 这是最有效的一招。**只看"有没有报错"是没用的** —— 本仓 `uestc-news`
   曾因为正则写死了 `class="title"`（实际有两种模板：`class="title"` 和 `class="title l2"`），
   只命中 4 条，**看起来完全正常，实际漏抓 90%**。放宽成 `class="title[^"]*"` 后 4 → 49。
4. **改 `sources.json` 里的 `item_pattern` / `date_pattern` / `list_selector`**（改完必须跑
   `--dry-run --verbose`，看命中数是否回到正常量级）。
5. 顺手把这次的发现写进该源的 `notes`。下一个人会需要它。

### 9.4 加一个新源

在 `sources.json` 的 `sources` 数组里加一个对象，字段含义：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一标识，也是输出文件名（`content/collected/<id>.json`）。用 `机构-栏目` 风格 |
| `name` | ✅ | 展示名，会写进每条记录的 `source.name`（页面上显示"信息来源：…"） |
| `url` | ✅ | 列表页地址 |
| `category` | ✅ | `competition` 或 `campus` |
| `priority` | ✅ | 1=官方聚合 / 2=校级栏目 / 3=补充 |
| `enabled` | ✅ | 抓不到就设 `false`，**并在 `notes` 写清原因** |
| `encoding` | ✅ | 一般 `auto`；确认是 GBK 就写 `gbk` |
| `fetch` | ✅ | 目前只支持 `html` |
| `base_url` | | 相对链接的基准（`urljoin` 用） |
| `url_template` | | 链接不是路径时用，如 `…/info/{href}`（教务处 href 是 newsId） |
| `list_selector` | | 极简 CSS：`tag.class` / `#id` / 空格或 `>` 分层。**只用于"容器还在不在"的预检** |
| `item_pattern` | ✅ | 正则，**必须含 `(?P<href>…)`**；带 `(?P<title>)`/`(?P<date>)` 更好 |
| `title_pattern` | | `item_pattern` 没抓标题时，对条目片段二次抽取（也要有 `(?P<title>)`） |
| `date_pattern` | | 同上；**优先取最后一个捕获组**，别把属性名带进 `date_text` |
| `date_year_policy` | | `published`（默认）或 `deadline`，见 §5.3 |
| `notes` | ✅ | 实测记录：UA、返回码、字节数、命中数、坑在哪 |

`item_pattern` 会以 `re.S` 编译（`.` 匹配换行），所以跨行写 `.*?` 是安全的。

**加源模板**（复制改）：

```json
{
  "id": "example-site-news",
  "name": "某某官网 · 通知公告",
  "url": "https://example.edu.cn/notice",
  "category": "competition",
  "priority": 3,
  "enabled": false,
  "encoding": "auto",
  "fetch": "html",
  "base_url": "https://example.edu.cn",
  "list_selector": "div.notice-list li",
  "item_pattern": "<li[^>]*>\\s*<a href=\"(?P<href>[^\"]+)\"[^>]*>(?P<title>[^<]+)</a>\\s*<span[^>]*>(?P<date>[^<]+)</span>",
  "date_pattern": "(\\d{4}-\\d{1,2}-\\d{1,2})",
  "notes": "实测 2026-10-15：HTTP 200…（先填实测结果，再决定要不要 enabled:true）"
}
```

**加源标准动作（照这个顺序做，别跳步）：**
1. 浏览器「查看网页源代码」，确认能看到标题（服务端渲染才值得做）。
2. `curl -s -A "<我们的UA>" <url> -o /tmp/x.html`，看返回码和字节数。
3. 写正则，在 Python 里数命中数（见 §9.3 第 2 步）。
4. 填进 `sources.json`，`enabled` 先设 `false`。
5. `python3 scripts/collect.py --source <新id> --dry-run --verbose` 看命中数和日期抽取率。
6. 满意了再把 `enabled` 改成 `true`，正式跑一次。
7. 把实测数据写进 `notes`。

## 10. 日常运维

仓库使用 `.github/workflows/pages.yml` 统一运行采集、网页生成、校验和发布，计划每天北京时间 03:10 开始。手动运行入口为 Actions → Update and deploy website，可选择来源及试运行。机器人提交后的发布在同一次运行中完成。

来源健康与新增条数见 Actions 运行摘要。全部来源失败时流程停止；部分失败时保留相应旧资料并报告异常。内容没有变化时不重写来源 JSON。运行状态和异常记录通过 Actions 缓存保留，缓存未命中时使用现有 JSON 继续去重。

```bash
# 每周看一眼有没有累积的异常
python3 -c "import json;d=json.load(open('content/collected/_anomalies.json',encoding='utf-8'));from collections import Counter;print(Counter(x['rule'] for x in d['items']))"

# 彻底重置某个源（慎重：会忘掉去重记忆，下一轮已发布条目会被当新条目重算）
#   删掉 _state.json 里该源的 seen_ids，即可让它重新评估曾被 Guard 拦截的条目
```

**提交前检查**：`content/collected/*.json` 里不该出现 `locked: true` 的条目被改动；
`_anomalies.json` 里不该有 `null-overwrite` / `jump-too-large` 这类**逻辑类**异常堆积
